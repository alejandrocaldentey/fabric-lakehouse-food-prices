# ADR 0013 — Semantic model: Direct Lake on OneLake, generated as TMDL from the metric catalogue

- **Status:** Proposed
- **Date:** 2026-11-26

## Context

[ADR 0006](0006-diamond-metrics-layer.md) made `metrics/metrics.yaml` the only place a metric is defined and promised that the DAX measures of the Fabric semantic model would be generated from it. Two choices are open:

1. **Storage mode** — how the semantic model reads the gold lakehouse.
2. **Authoring** — how the model gets built and changed: by hand, by a notebook, or as code in Git.

A third question rides on both: the Fabric data agent should answer natural-language questions **only** with governed numbers, so the model has to expose measures, not raw columns.

## Options considered

### Storage mode

| Option | Freshness | Copy of the data | Limits | Fits when |
|---|---|---|---|---|
| Import | At each refresh | Yes, compressed in the model | Refresh CU and time grow with the data | Sources outside OneLake, heavy calculated columns |
| Direct Lake on the SQL analytics endpoint | As soon as the endpoint metadata syncs | No | Falls back to DirectQuery above guardrails or on SQL views and SQL security; depends on endpoint sync lag after each write | Models that need SQL views or SQL-level security |
| **Direct Lake on OneLake** | As soon as the Delta commit lands | No | No DirectQuery fallback: a query above the SKU guardrails fails instead of slowing down; no SQL views | Delta tables already shaped for reading — this product, where Diamond is an aggregate table |

### Authoring

| Option | Reviewable | Repeatable across dev → prod | Single definition of a metric |
|---|---|---|---|
| Built by hand in Power BI Desktop or the web | No | No | No — DAX is retyped |
| Notebook with semantic-link-labs writing measures to a live model | Partly (the notebook is code) | Yes, per workspace | Only if the notebook reads the catalogue |
| **TMDL generated from the catalogue, committed, deployed by Fabric Git integration / fabric-cicd** | Yes, every change is a diff in a pull request | Yes, the same folder deploys to every workspace | Yes |

## Decision

**Direct Lake on OneLake, authored as TMDL generated by `python -m semantic.build`.**

- [`semantic/model.yaml`](../../semantic/model.yaml) says which tables, relationships, hidden columns and number formats the model has. It holds no formula.
- Measures come from the metric catalogue: one per metric that is not `deprecated`, named by its label, described by its description, filed under a *Certified* or *Experimental* display folder and annotated with the catalogue name.
- A new catalogue field, `rollup`, says what a metric means above its grain. `mean` returns the unweighted mean of the country-year values in the filter; `none` returns blank unless exactly one country and year is selected. The pass-through ratio is `none`: the mean of ratios is not a ratio of means, so the model refuses to show it rather than show something wrong.
- Every metric column of `diamond_country_year` is hidden. Report authors and the data agent see measures only.
- Column names and types are read from an empty local build of the pipeline, so the model cannot reference a column the SQL does not produce.
- The build fails on a measure that reads a missing column, a relationship to a missing column, a unit without a number format, two metrics with the same label, or unbalanced DAX. CI fails if any generated file is stale.
- Lineage tags and the item's logical id are derived from object names, so regenerating the model never changes them and reports stay bound.
- The workspace and lakehouse ids in the OneLake expression are placeholders replaced per environment at deployment (backlog: Fabric workspace and dev → prod with fabric-cicd).
- The **data agent instructions** ([`fabric/data-agent/instructions.md`](../../fabric/data-agent/instructions.md)) are generated from the same catalogue: answer only with listed measures, state the country and year, say when a value is an unweighted mean, flag experimental measures with their caveat.

## Cost per scenario

No new line item in [`cost/model.yaml`](../../cost/model.yaml): Direct Lake runs on the Fabric capacity already costed, and authors already need a Power BI Pro licence.

| Scenario | What changes against Import | Data agent |
|---|---|---|
| Demo / PoC (F2, paused outside runs) | No refresh CU and no second copy of the data; the tables have hundreds of rows, far inside the smallest SKU's guardrails | Questions consume capacity CU. Price per question and availability on a trial capacity: **to verify** before the demo |
| SME (F8, always on) | Saves the import refresh on every hourly run | Same; budget it as a share of the capacity and watch the Capacity Metrics app |
| Enterprise (F64, 10 TB+) | The saving grows with the data, and so does the risk of hitting guardrails, where OneLake mode fails rather than falls back. Mitigation: serve aggregate tables (Diamond already is one) and keep raw facts out of the model | Viewers on F64 need no Pro licence; agent usage still consumes CU |

## Consequences

- ✅ One definition per number from SQL to DAX to the agent's instructions; a metric change is one YAML diff that regenerates SQL, DAX, docs and agent text.
- ✅ The model is reviewable in pull requests and deploys identically to every workspace.
- ✅ The agent cannot reach an ungoverned column: metric columns are hidden and its instructions list measures only.
- ⚠️ The generator validates structure, not DAX semantics: there is no DAX engine in CI. After the first deployment, a control query per measure must match the Diamond table (to add with the deployment item).
- ⚠️ Measures are on the fact table (`diamond_country_year`), not a dedicated measure table: an empty measure table would need a calculated or import table, and the model stays pure Direct Lake. Display folders keep them readable.
- ⚠️ There is no shared year dimension yet: `diamond_country_year[year]` and `fact_price_annual[year]` filter separately.
- ⚠️ Time-intelligence measures that only make sense in DAX are not generated; when needed they are added in the model spec and listed in the catalogue as DAX-only (ADR 0006).

## When we would revisit

- The model needs SQL views or SQL-endpoint security → Direct Lake on the SQL endpoint.
- Tables approach the SKU's Direct Lake guardrails → aggregate tables, a bigger SKU or Import for the heavy table.
- A second BI tool or many more consumers need the same measures → a dedicated semantic layer (dbt Semantic Layer, Cube), as ADR 0006 anticipates.
